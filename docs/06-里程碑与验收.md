# 06 · 里程碑与验收

## 1. 前置 Spike（每个 ≤ 0.5 天，M0 内完成，**结论回写本文档**）

| ID | 实验 | 成功判据 | 影响 |
|---|---|---|---|
| S1 | MinerU 插件能否作为**知识管道提取节点** | 管道里上传 PDF → 输出 Markdown（表格/公式保留） | 决定走管道 vs 后端预转 Markdown |
| S2 | 后端调 `create-by-text` 分块 512/50 是否按预期 | 中文文档生成块数 ≈ 总字数/462；块长分布合理 | 确认"字符单位"结论与调参 |
| S3 | `/chat-messages` streaming 的 `retriever_resources` 完整性 | 每轮回答都能拿到 segment_id / score / content | 引用功能能否按设计实现 |
| S4 | Moderation 自定义端点接入流式输出 | 100 字符分段回调、命中后能中止输出 | 输出审核方案定案 |
| S5 | 阿里云内容安全 SDK 联通 + 账单口径 | 文本/图片各一次成功调用，返回 label | 审核卡点可行性 |

## 2. 里程碑

### M0 · 环境与 Spike（2 人日）
**交付**：Dify 1.17.0 Docker Compose 起好（含 PostgreSQL / Redis / 向量库）；MinerU 服务本地或 API 可用；`FILES_URL` 等变量核对完毕；Spike S1–S6 结论表。
**验收**：Dify 控制台上传一份 PDF 能问答出正确结果；后端能连通 Dify App API 与 Dataset API（各一次 200）。

### M1 · 后端骨架 + 数据库（3 人日）
**交付**：FastAPI 骨架、`.env` 配置、Alembic 首版迁移（本文档全部表）、JWT 认证、统一响应与错误码、结构化日志、`tenant_id` 注入依赖。
**验收**：`alembic upgrade head` 一次通过；`pytest` 覆盖登录、越权（跨租户访问返回 40401）用例通过。

### M2 · 知识库与文档管理（5 人日）
**交付**：KB CRUD（同步 Dify dataset）、成员与权限、上传编排（存盘 → 审核 → MinerU 解析 → `create-by-text` 入库 → 状态机）、任务 worker 与重试、文档列表/详情/重试/删除、分块查看。
**验收（逐条演示）**：
1. 上传 PDF/DOCX/PPTX/MD/PNG 各 1 个，全部到达 `status=ready` 且 `chunk_count>0`；
2. 分块参数确认为 512/50（在 Dify 段落页可见）；
3. 重复上传同一文件 → 命中 `40901` 或复用既有文档，不重复入库；
4. 上传含违规文本/图片 → 拒绝入库，`audit_log` 有记录；
5. 越权：用户 B 访问用户 A 的 KB 文档 → `40401`；
6. 杀掉 worker 再重启 → 未完成任务继续执行（`FOR UPDATE SKIP LOCKED`）。

### M3 · RAG 问答（4 人日）
**交付**：`chat-qa` Chatflow 上线；后端 SSE 代理；引用映射与 `sources` 事件；会话与消息归档；开启输入/输出审核。
**验收**：
1. 提问后**首字延迟 ≤ 3s**，端到端回答完整；
2. 回答中引用编号可点击，展开显示原文片段（来自 KB 原文）；
3. 无相关内容时返回"未找到"提示而非编造；
4. 提问/回答违规 → 前端 `moderation` 事件提示，`audit_log` 落库；
5. 刷新页面后历史提问可见，且能继续追问（上下文连贯）。

### M4 · 智能出题（4 人日）
**交付**：`workflow-quiz` Workflow；四种题型生成；后端校验与落库；简答题评分 Workflow；作答判分。
**验收**：
1. 选择单/多/判断/简答 4 种题型各 3 题，10 次生成中 **JSON 解析成功率 100%**（Code 节点兜底）；
2. 单选题答案必在选项中；多选题答案 ≥ 2 项；判断题答案为布尔；
3. 每题带解析，且能显示"出自哪份资料/哪个片段"；
4. 客观题判分与标准答案一致；简答题给分合理（人工抽查 10 题，偏差 ≤ 10 分）；
5. 题型/题量/难度三参数组合任意切换不报错。

> **2026-09-15 真机验证记录（App C 简答判分）**
>
> - 判分质量（直连 App C，真实材料）：半懂 → 50 分（命中「原子性/隔离性」，遗漏「一致性/持久性」）；
>   完整 → 100 分（4 点全中、无遗漏）；空答 → 0 分。命中/遗漏要点与评语均逐项正确。
> - 后端链路：登录 200 → 出题 201 → 交卷 200（`score=90`、`is_correct=true`、feedback/analysis 非空）
>   → 错题本 200 → 删除 200。
> - 踩坑（已修 + 已加静态校验）：**节点 id 只能 `[A-Za-z0-9_]`**。带中划线时 Dify 不会替换 Prompt 里的
>   `{{#节点id.变量名#}}`，模型收到字面文本 → 判分恒为 0 分；而 `value_selector` 结构化选择器不受影响，
>   症状极具迷惑性。详见 `dify/README.md` §4「节点 id 规则」。
> - 尚未覆盖：本条验收第 1 项（10 次生成 JSON 成功率 100%）与第 4 项后半（人工抽查 10 题偏差 ≤ 10 分）
>   仍需完整抽样。

> **2026-09-15 真机验证记录（出题必须出自知识库文档，缺陷修复）**
>
> - 缺陷现象：生成的题目只跟知识库**名称**有关（如库名 `rag` → 一整套通用 RAG 题），与库里的文档无关。
> - 根因（三层，均已修）：
>   1. **后端没把文档原文交给 App B**：只下发一个 40 字的 `topic`（≈首段前 40 字或库名），
>      而 App B 内「知识检索」节点只能**静态勾选**某个库、查询词还是 `topic` → 题源不受所选知识库控制；
>   2. **检索把有效正文挡在门外**：KB 相似度阈值 0.5 下，命中的两条恰好是内容只有 `---` 的碎片块
>      （实测该库 9 条命中里只有这 2 条过阈值）→ 资料 66 字 → 模型只能按库名编题；
>   3. **碎片块的来源**：入库用 `separator="\n\n"` 切块，Markdown 的分隔线 `---` 被切成 3 字符独立块，
>      既占检索 top_k 又可能高分胜出。
> - 修复：后端按所选知识库多路检索（主题/库名/文档名）→ 合并去重 → **过滤无内容碎片** →
>   阈值挡光时放宽阈值重取 → 把【资料】作为 `context` 下发给 App B（Prompt 以【资料】为唯一出题依据）；
>   入库前清洗 Markdown 装饰线（表格分隔行不受影响），已有文档「重新入库」时自动重建 Dify 文档。
> - 真机复验（`DIFY_MODE=http`，api.dify.ai）：
>   - KB「rag」→ 题目改为考文档里的 Prompt 模板内容，解析直接引用文档原文
>     （与原文最长公共片段 **49 字**）；KB「2」→ 引用 18 字连续原文；
>   - 入库清洗：3 个库分别 8→7、12→10、17→15 块，**碎片块 1/2/2 → 0**；
>   - `pytest` 66 passed；`scripts/check_dify_dsl.py` ALL OK（App B 断言已含 `context` 入参与【资料】口径）。
> - 运维提示：**App B 需要加一个 Start 变量 `context`（段落、非必填）并按 `dify/prompts/quiz_generate_system.md`
>   更新 Prompt**，才能走「干净路径」（否则后端退化把资料并入 `topic`，题目虽已出自文档，但 App B 检索节点
>   绑定的旧库内容仍可能混入）。步骤见 `dify/README.md` §5。

### M5 · 错题本与历史（3 人日）
**交付**：错题自动登记（含 `wrong_count` 累加）、状态流转（未掌握/复习中/已掌握）、删除；对话历史列表/详情/重命名/删除；错题与历史筛选。
**验收**：
1. 同一题答错两次 → `wrong_count=2`，只出现一条错题记录；
2. 标记已掌握后从"未掌握"列表消失，可被"已掌握"筛选到；
3. 再次答错已掌握的题 → 自动回到"未掌握"；
4. 删除历史会话 → 列表消失，数据软删可追溯。

### M6 · 前端 Polish + 审核完善（3 人日）
**交付**：上传进度、状态徽标、空态/错误态、加载骨架；审核拦截提示文案统一；审核日志查看页（管理员）。
**验收**：全流程无阻断性 bug；上传进度与真实状态一致；审核命中提示清晰可重试。

### M7 · 联调、压测与交付（2 人日）
**交付**：部署脚本（Nginx + Compose）、运维手册、演示脚本、已知限制说明。
**验收**：陌生环境按文档 1 小时内完成部署；并发 10 用户问答无错误；所有 MVP 需求演示通过。

**合计 ≈ 26 人日**（不含 Spike 内不可控的 MinerU 部署调试）。对比纯自建方案（约 39 人日）节省约 13 人日。
